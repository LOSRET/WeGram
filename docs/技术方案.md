# WeGram 技术方案 v0.2

> 目标:Windows 桌面端、微信前端风格的 Telegram **完整客户端**(登录自己的账号,可见全部会话/群/频道)。
> 本文档只做技术决策与落地设计,不含实现代码。
> 状态:决策已锁定(v0.2)。原 §15 的 4 个开放问题已全部拍板并回写正文,见 §15 决策记录。
> 剩余待验证项(#2 登录链路、#3 虚拟列表帧率)必须先跑通再进入正式开发。

## 0. 决策摘要

| 问题 | 决策 | 一句话理由 |
|---|---|---|
| 桌面壳 | **Electron(主选)**,Tauri 列为 v2 选项 | 协议库是 Node 原生的,Tauri 需要额外塞一个 Node/Bun sidecar,省不下复杂度 |
| 协议层 | **TDLib + `tdl`(主选)**,`teleproto` 为备选 | 你要「完整」,完整度的天花板由协议库决定;后期换库是灾难,所以一次选对 |
| 消息存储 | **交给 TDLib** 自带的本地库,不自己建消息表 | 避免重复造 DB + 手工处理 `pts/qts/seq` 追赶 |
| UI | React 19 + TS + Vite(electron-vite) | — |
| 样式 | Tailwind v4 + CSS 变量 token | 换肤 = 换 token,不动组件 |
| 状态 | Zustand + TanStack Query | 局部 UI 态与请求缓存分离 |
| 分层 | renderer 不含任何协议知识,只认 `window.tg.*` | 这是后面能换协议库、能并行开发 UI 的唯一保障 |
| 账号 | **v1 单账号**,多账号进 v2 | 省掉账号切换 UI 与 TDLib 实例池,排期才站得住 |
| 贴纸 | **v1 就要动图**:静态 WebP + TGS(Lottie)+ WebM 三种都要渲染 | 自用体验底线,动图走占位会让聊天界面像半成品 |
| 代理 | **v1 内置 SOCKS5 + MTProxy**,带设置页与连通性测试 | 国内网络是刚需;后补会牵动 TDLib 启动流程与登录顺序 |
| 工期 | **5 周**出可自用版本(4 周基线 + 动图贴纸 + 代理 − 省下的多账号) | 见 §11 |

## 1. 范围

### 目标(MVP 必须有的)

- 登录:手机号 + 验证码 + 两步验证(2FA),session 持久化
- 会话列表:私聊 / 群 / 频道,未读数、置顶、免打扰、最后一条消息预览
- 聊天:历史分页、发文本、回复、编辑、删除、转发
- 媒体:图片(含相册)、文件,上传/下载进度、缩略图
- 贴纸与自定义 emoji:静态 WebP、TGS(Lottie 动画)、WebM 视频贴纸三种都要渲染;自定义 emoji 复用同一套贴纸文件管线
- 网络:设置页内置 SOCKS5 / MTProxy 代理,可测试连通性并热切换
- 交互态:已读回执、typing、在线状态
- 搜索:会话内搜索 + 全局会话搜索
- 微信皮肤:浅色 + 暗色,气泡/输入栏/列表/长按菜单
- 打包:Windows 安装包 + 自动更新

### 非目标(明确不做,避免工期失控)

- **语音/视频通话**:Telegram 用的是自研 P2P + 私有信令,不走 TDLib 的公开 API,基本等于重写。永久不做。
- **秘密聊天(E2E)**:TDLib 有相关类型,但坑多、调试成本高。v1 不做,v2 评估。
- 多账号:v2。v1 只支持单账号(v0.2 决策),`accounts` 表保留但只会有 1 行,账号切换 UI 不做。
- 朋友圈 / 小程序:Telegram 没有对应实体,硬塞只会两边不像。
- 移动端:本方案不覆盖。

## 3. 协议层选型

### 3.1 候选对比

| | TDLib (+`tdl`) | teleproto | MTKruto |
|---|---|---|---|
| 维护方 | Telegram 官方 | 社区 fork(GramJS 归档后的接盘) | 个人项目,dcdunkan |
| 完整度 | ★★★★★ 官方客户端同源 | ★★★☆ | ★★★ |
| 增量同步 | 内置,不用管 `pts/qts/seq` | 需自己 `updates.GetDifference` 追赶 | 需自己处理 |
| 本地消息库 | 有(可关) | 无,要自己建 | 无,要自己建 |
| Windows 依赖 | 需要 `tdjson.dll`(有预编译) | 纯 JS,零原生依赖 | 纯 TS,零原生依赖 |
| 学习曲线 | 陡(JSON API + update 流) | 平(就是 GramJS 那套) | 平 |
| 风险 | 升级偶有 breaking | fork 成熟度需实测 | 未到 1.0,作者不建议关键项目 |

> 背景:GramJS(`gram-js/gramjs`)已于 2026-07 **归档**。仍在更新的两条线是官方 TDLib 与社区 fork teleproto(保持 `StringSession` wire 兼容)。

### 3.2 结论:主选 TDLib

理由是三条硬指标上 TDLib 不是「好一点」而是「另一个量级」:

1. **消息不会丢。** 断网 3 天回来,`pts` 追赶、频道补历史、删除/编辑回放全部由 TDLib 处理完再吐给你。纯 JS 实现这块要自己写状态机,写对很难,写错的表现是「偶尔少几条消息」——这种 bug 用户会记一辈子。
2. **消息库可直接用。** `use_message_database = true` 后,冷启动的会话列表和历史都在 TDLib 里,你的 SQLite 只存 UI 态。省掉整个「消息表 + 索引 + 迁移」模块。
3. **媒体处理全包。** `file_id` 生命周期、缩略图多尺寸、分片下载、`downloadFile` 断点续传,官方客户端那套直接可用。自己实现图片/视频的下载调度是个无底洞。

`tdl` 是 TDLib 的 Node 封装,配 `prebuilt-tdlib` 可免去 C++ 编译——**这是本方案能否成立的前提条件,先验证**(§0 Spike 1)。

### 3.3 Plan B:teleproto

触发条件(任一):

- `prebuilt-tdlib` 在目标 Windows 版本/架构上装不上,且短期无解;
- TDLib 的 IPC/JSON 开销导致列表滚动卡顿(理论上不会,但要实测);
- 需要更细的协议控制(自定义 TL 方法)。

切换成本:重写 `src/main/telegram/tdlib/**` → `teleproto.ts`,补齐自建消息表(§5.3)+ `GetDifference` 追赶逻辑,预估 **+5~7 人日**。UI 零改动。

> ⚠️ 不要选 GramJS 原仓库。归档 = 协议再有变更无人修。

## 4. 桌面壳:为什么是 Electron 而不是 Tauri

| | Electron | Tauri 2 |
|---|---|---|
| 安装包 | ~100–150MB | ~10–20MB |
| 内存占用 | ~200–300MB | ~80–120MB |
| **跑 Node 协议库** | **原生支持,主进程就是 Node** | 需要 Bun/Node sidecar,自己管进程生命周期、崩溃重启、IPC |
| 协议库换成 Rust 绑定 | 不需要 | 若走 TDLib 要写 Rust FFI,构建链痛苦 |

你的核心依赖(`tdl` / `teleproto`)是 Node 原生的。选 Tauri 就等于:为了省 100MB 安装包,自己实现一个 sidecar supervisor。对单人项目这是负收益。

**结论:v1 用 Electron。** v2 若安装包体积成为真实痛点,再评估 Tauri + `bun build --compile` 的 sidecar 方案(此时 `telegram/` 目录已是干净的适配层,迁移面可控)。

技术要点:

- `contextIsolation: true`,`nodeIntegration: false`,`sandbox: true`
- 只通过 preload 暴露白名单 API,渲染层拿不到 `require`
- 显式 `Content-Security-Policy`,禁止 `webSecurity: false`
- 构建用 `electron-vite`,打包用 `electron-builder`(NSIS + 自动更新)
- pnpm workspace 下原生模块要求 `.npmrc` 设 `node-linker=hoisted`

## 5. 数据层

### 5.1 归属划分(重要)

| 数据 | 归属 | 说明 |
|---|---|---|
| 会话、消息、用户、群成员、文件元数据 | **TDLib 本地库** | 不复制,不自己建表 |
| 草稿、每条会话的滚动位置、窗口尺寸、UI 偏好 | 本地 SQLite(`ui.db`) | 小、与协议无关 |
| 会话全文搜索 | TDLib 内置 `searchChatMessages` | 不做自己的索引 |
| 全局搜索(会话) | TDLib 内置 `searchChats` | 离线匹配已知会话的标题/用户名,同样不自建索引 |
| 凭据/session 加密密钥 | Windows DPAPI(`safeStorage`) | 不落明文 |
| 媒体文件 | 磁盘缓存目录 + LRU | 按 size 上限清理 |

> 与 Plan B 的差异:若换 teleproto,第 1 行变成「自建 SQLite 消息库」。所以 `ui.db` 与「协议库」要放在两个不同文件,别混。

### 5.2 `ui.db` schema

实现说明(v0.3):用 **Node 内置 `node:sqlite`**(Electron 45 自带 Node 24.22 已支持),不用 `better-sqlite3`。
理由:原生模块要按 Electron ABI 重建(`@electron/rebuild` + MSVC),而内置模块零依赖、免重建;
代价是它在上游仍标记 experimental,所以**所有 SQL 只出现在 `main/store/ui-db.ts` 一个文件里**,
将来若 API 变动,换回 `better-sqlite3` 只改这一处。表结构按原设计不变:

```sql

## 6. 同步与连接

### 6.1 TDLib 路线

- 一条 `update` 长流:`client.on('update', ...)`,**必须**在主进程单点消费。
- 主进程侧做 **50–100ms 合批**(`requestAnimationFrame` 等价的定时聚合),避免每条消息一次 IPC 打爆渲染层。典型群聊爆发时,未合批会产生上千次 IPC/秒。
- 关注的关键 update:`updateNewMessage` / `updateMessageContent` / `updateDeleteMessages` / `updateChatReadInbox` / `updateChatReadOutbox` / `updateChatPosition` / `updateChatUnreadMentionCount` / `updateConnectionState` / `updateFile` / `updateUserStatus` / `updateChatAction`(typing)。
- 连接状态机:`AuthorizationState`(登录)与 `ConnectionState`(网络)是两套,UI 要分别显示。`authorizationStateReady` 之前所有查询会返回 401,别提前发请求。
- 错误处理:429 带 `retry_after`,必须退避,**不要重试风暴**。
- **启动阶段单独成一个状态机**:`AuthState`/`ConnectionState` 都回答不了「根本起不来」(tdjson 加载
  失败、数据库打不开、客户端自己退出)。主进程维护 `BootState`(`starting` → `opening` →
  `connecting`/`offline`/`updating` → `ready`,以及终态 `failed`/`crashed`),登录窗用它显示
  具体进度;终态必须停掉转圈并给出原因与出路,不能再让「正在连接」无限转。`opening` 来自
  `authorizationStateWaitTdlibParameters`,连接阶段来自 `updateConnectionState`(代理与否单独保留),
  `failed` 是 `adapter.start()` 抛出,`crashed` 是客户端未经 `stop()` 自行 close。0.1.1 安装包的
  tdjson 路径错误就属于 `failed`,当时只写日志,所以窗口永远停在「正在连接」。

### 6.2 Plan B(teleproto)

- 断线重连后先 `updates.getState()` 与本地 `sync_state` 比对,不一致则 `updates.getDifference` 补齐。
- `pts` 出现跳变且无法补齐时,必须降级为「重拉该会话最近 N 条」,不要静默丢消息。

### 6.3 分页

- 历史消息:游标式向后翻页,`limit = 30`(首屏 50)。
- 不要用 offset 分页——消息会插入,offset 会漂移。
- **实测结论(必须照做)**:`getChatHistory` 的 `from_message_id = 0` 不触发服务器拉取,只返回本地缓存的最后一条。首屏必须锚定 `chat.last_message.id`;向后翻页用上一页最旧那条的 id,并在应用层过滤掉「严格不小于锚点」的消息。
- `offset` 的负数是「取比锚点更新的消息」,不能用来向后翻页;统一 `offset: 0` + 客户端过滤。

### 6.4 代理(SOCKS5 / MTProxy)

- 统一走 TDLib 的 `addProxy`:`proxyTypeSocks5`(host/port/username/password)与 `proxyTypeMtproto`(host/port/`secret`)。
- **实测:无代理时 `getChats` 会一直挂住**(连接掉到 `connecting`),而 `getMe()` 读本地库仍成功——表现是「已登录但列表永远空」。代理是硬前置,不是可选优化。
- **时序硬约束**:必须在 `authorizationStateWaitTdlibParameters` 之后、任何网络请求(`getMe`/登录)之前设置完。否则首个请求会走直连超时,用户看到的是「登录按钮没反应」。
- 连接态只信 `updateConnectionState`,不要自己推断;`connectionStateWaitingForNetwork` 与代理配置错误要能区分展示。
- 配置持久化:类型与地址存 `ui.db` 的 `app_settings`(key `proxy`),**密码/`secret` 用 `safeStorage` 单独加密**后再落盘,渲染层只拿掩码。
- 切换代理 = `disableProxy` → `addProxy` → `enableProxy` → 触发重连,运行中不直接改参数。
- 设置页「测试」按钮:用一次性客户端带该代理调 `getMe`,5s 超时判定,不做后台常驻探测(避免重试风暴与 429)。

## 7. IPC 契约

`packages/protocol` 用 zod 定义,主/渲染共享类型,单一事实来源。

### 7.1 命令(renderer → main,request/response)

| 通道 | 入参 | 出参 |
|---|---|---|
| `auth:state` | — | `AuthState`(渲染层启动时拉当前授权态,订阅前用) |
| `auth:start` | `{ phone }` | `{ state }` |
| `auth:code` | `{ code }` | `{ state }` |
| `auth:password` | `{ password }` | `{ state }` |
| `auth:qr` | — | `AuthState`(请求二维码;链接经 `evt:auth` 的 `waitQr` 到达) |
| `auth:reset` | — | `AuthState`(销毁并重建 TDLib 认证实例,取消二维码,回到 `waitPhoneNumber`) |

## 8. 渲染层设计

### 8.1 状态分片

| 关注点 | 方案 |
|---|---|
| 会话列表、当前会话 ID、连接态、UI 面板开关 | Zustand(可序列化部分持久化) |
| 消息分页、搜索结果、用户资料 | TanStack Query(按 `chatId` 做 query key,`staleTime: Infinity`,靠事件 `setQueryData` 更新) |
| 输入框文本、IME 组合态 | 组件本地 `useState` + ref,不进全局 store(高频变更) |
| 大对象(ImageBitmap、已解码贴纸) | 独立的 Map 缓存 + 显式释放,不进 React 状态 |

> 反模式:把消息数组放进 Zustand 全局 store。几千条消息每次更新都会通知所有订阅者,输入框会跟着卡。

### 8.2 聊天列表:滚动与锚定(最容易做砸的部分)

必须同时满足 4 条,缺一条体验就崩:

1. **进会话的落点**分三档:① 有保存的阅读位置,且它不在未读边界之前 → 恢复那一行;② 否则有未读消息 → 落到「以下是新消息」分隔线,分隔线贴视口顶,下面全是新消息;③ 都没有 → 落到最新消息。落点必须和首屏数据一致:目标行(保存位置或未读边界)不在最新一页时,用 `messages:around` 直接取「以目标为中心的窗口」再挂载列表(列表只在首帧捕获一次位置)。**不再从最新页往回翻固定页数**:那会把可达深度钉在 6~8 页,预算一用完就只能落到最旧已加载行。窗口若没有到达最新消息,响应带 `hasNewer: true`:新消息先排队(不能直接拼到窗口末尾,否则中间会缺一段),读者往下滚到窗口底时用 `messages:newer` 继续补页,浮标显示「跳转到最新消息」并在点击/发送前用最新一页替换窗口;替换后用每个会话的跳转信号把视口落到底部。未读总量不足一屏时分隔线顶不到视口顶,滚动器自然 clamp 到底部,分隔线仍在上方可见。整个定位过程在列表隐藏(`--pending`)状态下完成,不能出现「先闪顶部再跳」。
2. **向上加载历史时视口不跳**。记住 `distanceFromBottom`,插入后 `scrollTop = newScrollHeight - oldScrollHeight + oldScrollTop`。用 `requestAnimationFrame` 对齐,避免抖动。**旧页必须提前取,不能到顶才请求**:TDLib 的旧页来自本地缓存或服务器(实测第一个服务端回答约 3.4s),而滚轮从任意位置滑到顶部只要一两秒,到顶才发请求必然表现为「滚轮咬住不动」。列表在挂载时、以及每次翻页落地后各预取一页存进 `olderPagesByChat`(只存不进消息列表),到顶时只做插入;预取页在其中的消息被删除/编辑、或窗口被 `setHistory` 替换时立即作废,否则会把已删除的消息重新插回列表。
3. **只有贴底才自动滚**。阈值 40px。不贴底时右下角显示「跳转到最新消息」浮标,有新消息到达时文案变成「N 条新消息」,点击滚到底。浮标上的 N 只算**还没看到**的新消息:每有一条新消息滚进视口就减 1(再往上滚不会加回来),滚到底或点浮标归零——计数是「还剩几条没看」,不是「一共来了几条」,否则读者一条条读完,浮标还在喊「6 条新消息」。这个 N 不是累加出来的,而是**由已读标记推出来的**:见下一条,浮标、会话红点、左栏未读数共用同一个来源(「比 read marker 新、且还在视口下面」),三处同进同退。浮标由「是否贴底」决定,不是由「有没有新消息」决定——按阅读位置重开、或停在未读分隔线上的会话同样需要它。**已读回执按「真的看到过」逐条推进**:视口里出现过的最新一条就是上报的 `upTo`(另需窗口可见 + 窗口聚焦,`lib/readGate.ts`)。TDLib 的 read marker 单调前进,`unread_count` 由服务器回推,所以读者往下滚、逐条看过新消息时,浮标、会话红点、左侧栏未读数一起减;没进过视口的新消息保持未读,否则就是「没看到也算读了」。上报带 350ms 去抖,一串到达合并成一次 `viewMessages`;这和官方客户端一致:看过即已读,并且同步到账号的其他设备。**打开会话本身不推进已读**:`chats:open` 只预热 `getChat`,否则点一下未读群会在正文落到「以下是新消息」之前就把 300 条未读清零,红点、左栏总数和其他设备都说「已读」,而读者眼前还是那一屏未读消息。`viewMessages(force_read: true)` 就是官方客户端用的同一个接口,服务器回报的 `last_read_inbox_message_id` / `unread_count` 经 `updateChatReadInbox` 回到渲染进程,所以「左栏未读数」不是本地估算,而是服务器状态。
4. **视口高度变化要补偿**。窗口 resize、输入框随内容长高、图片加载完成都会改变高度,统一走一个 `useAnchoredScroll` hook。

虚拟化用 `@tanstack/react-virtual`,动态高度必须开 `measureElement`。注意 `column-reverse` 与虚拟化组合会让 `scrollTop` 语义反转,建议**保持正向 DOM + 手动控制 scrollTop**,可维护性更好。

### 8.3 消息富文本渲染

Telegram 的消息格式是 TL **entities**(偏移 + 长度 + 类型),不是 markdown。必须自研渲染器:

```
entities: [
  { type: 'bold', offset: 0, length: 4 },
  { type: 'textUrl', offset: 12, length: 10, url: '...' },
  { type: 'code', ... }, { type: 'pre', language }, { type: 'spoiler' }
]
```

实现要点:

- 先按 offset/length 切成扁平片段树(支持嵌套),再映射成 React 元素;不要用字符串替换正则。
- 偏移是 **UTF-16 code unit**,含 emoji 时容易越界,必须写单测。
- `spoiler` 是**实心色块**遮罩(`--wx-spoiler`,纯黑)+ 点击揭示;会话列表的预览串里
  同样的字也要遮住,偏移由 `ChatSummary.lastMessageSpoilers` 带过来,但那里不可揭示
  (整行才是点击目标)。
- 自定义 emoji 走 `custom_emoji_id`,用 TDLib 的贴纸文件渲染,不能当普通字符。
- 链接必须做协议白名单(`https`/`tg`),防止 `file://` / `javascript:` 注入;非 Telegram 链接仍然
  交给系统(`shell.openExternal`)。
- **Telegram 自己的链接在应用内跳转。** `t.me/<用户名>[/<消息>]`、`t.me/s/…`、
  `t.me/c/<内部 id>[/<消息>]`、`tg://resolve`、`tg://user`、`tg://openmessage` 都解析成
  「会话 + 可选消息 id」:会话按用户名(`searchPublicChat`)、用户 id(`createPrivateChat`)或
  `t.me/c` 换算出的会话 id(`-1000000000000 - 内部 id`)打开;带消息 id 时先 `requestLocate`
  再激活会话,首屏直接按目标消息取窗口并定位高亮。纯解析在 `lib/telegramLink.ts`(单测覆盖各形态),
  打开在 `lib/openTelegramLink.ts`;邀请链接(`t.me/+…`、`joinchat`)和 `/addstickers`、
  `/share`、`/proxy` 这类「动作/网站页」没有对应能力,保持外链。Ctrl/⌘/Shift 点击或中键仍是
  浏览器的「在外面打开」语义。
- **`@提及` 是可点的会话入口。** TL 里有两种:`mention`(只带文本的 `@username`)和
  `mentionName`(带 `user_id`,没有用户名的人被「按 id 提及」时用它)。两者都渲染成蓝色可点文本,
  点击打开那个人的会话:带 id 的走 `chats:openPrivate`,`@username` 走 `chats:openUsername`
  (主进程用 `searchPublicChat` 解析;查不到时 toast 中文提示,不是默默失败);`@all` 指向整个群,
  不当作跳转目标;点到自己的账号只提示,不去开「文件传输助手」。打开不标记已读——`openChat` /
  `openPrivateChat` 的既有语义不变。

### 8.4 中文输入法(必测)

- 监听 `compositionstart` / `compositionend`,组合期间**禁用** Enter 发送和 `@提及` 补全。
- 用 `textarea` 而非 `contenteditable`:微信的输入栏没有富文本编辑需求,`contenteditable` 在 Windows 输入法下的坑(光标跳动、重复字符)远多于收益。
- 单测用例:拼音输入中按 Enter 不应发送;选词后 Enter 才发送。

### 8.5 媒体与贴纸渲染(W3 落地)

- **渲染层永远不接触文件路径。** 主进程把已下载文件注册为 `wx-media://f/<token>`,由 `protocol.handle` 流式返回(支持 Range,`<video>` 可拖动),CSP 的 `img-src`/`media-src`/`connect-src` 同时放行 `wx-media:`。token 只来自主进程注册表,请求 URL 不参与路径拼接。
- `MessageMedia` 只携带 `localUrl` / `thumbUrl` / `minithumbnail` 和尺寸;下载/上传进度单独走 `evt:file`,消息 DTO 保持不可变。
- TGS 用 Chromium 原生 `DecompressionStream('gzip')` 解压:压缩包 ≤2MB、解压后 ≤8MB、膨胀比 ≤80×,解码结果按 URL 做 LRU;lottie 实例在 `IntersectionObserver` 判定不可见时 pause,卸载时 destroy。
- WebM 贴纸交 `<video autoplay loop muted playsinline>`,同样离屏暂停;WebP 直接 `<img>`。
- **单个 emoji 的消息按贴纸渲染,不是文字。** TDLib 把「整条文本就是一个 emoji」的消息返回成 `messageAnimatedEmoji`(判定在 TDLib 的 `can_be_animated_emoji`,自定义 emoji 也走这条):正文是 AnimatedEmoji 整套里那张动画贴纸(TGS/WebM),另带点击音效 `animated_emoji.sound`。渲染成无气泡的 112 px 贴纸:收发各播一遍,点击重播并放音(官方 animated-emojis 文档:loop once when sent/received or clicked),所以 `StickerRenderer` 的 `playback="once"` 不能退化成循环;贴纸尚未解析出来(自定义 emoji 首次出现)时退回 48 px 字形。字形始终留在 `text` 里,供会话列表、引用和复制使用。
- **会员贴纸带第二份文件:特效。** Telegram Premium 的贴纸在 `Sticker.full_type.premium_animation` 里多带一条 TGS 特效,`messageSticker.is_premium` 是「这条消息要播特效」的开关;两者都成立时适配器才把特效文件写进 `MessageMedia.premiumEffectFileId`(已落盘时另带 `premiumEffectUrl`)。渲染层把它当作叠在贴纸上的一层装饰:正方形画布,边长 = 贴纸长边 × 1.49(官方 tdesktop 的 `kPremiumMultiplier = 1 + 0.245 * 2`),消息出现时播一遍、结束淡出,点击贴纸重播。它是独立文件,和贴纸一样等元素接近视口才下载,解压走同一套 gzip 守卫;解不出来就静默隐藏——特效坏了不能盖住贴纸。
- **会员自定义表情(custom emoji)按贴纸内联渲染。** Premium 的正文里可以内嵌自定义 emoji:TL 里是 `textEntityTypeCustomEmoji`,实体只带 `custom_emoji_id`,覆盖的仍是基础字形。主进程新增 `stickers:customEmoji`(`getCustomEmojiStickers`,单次最多 200 个 id),渲染层按 id 合并成一次请求、取回贴纸文档后长期缓存,文件按需下载;14 px 正文里以 20 px 贴纸替换字形,字形始终留在文本里(取不到、离线或未知 id 都回退字形,不出空洞)。整条消息只有一个自定义 emoji 的仍走 `messageAnimatedEmoji`(见上一条)。
- 图片/视频气泡在 DTO 尺寸到手时就占好最终盒子,缩略图先模糊占位:文件到达时行高不变化,否则会破坏 §8.2 的滚动锚定。

### 8.6 相册(Telegram media group)

Telegram 里「一条消息带两张图/两个视频」并不是单条消息:服务端存的是 2~10 条**独立消息**,它们共享同一个 `message.media_album_id`(int64,JSON 里是字符串),官方客户端把「相邻 + 同一发送者 + 同一 album id」的消息折叠成一个气泡。TDLib 没有「一条消息含多个媒体」的正常内容类型(`messageAlbum` 只在 `only_preview` 查询里出现),所以适配器只负责把 id 带到 DTO,折叠发生在渲染层。

实现约定:

- **协议**:`Message.albumId?: string`(`'0'` 视为不属于相册),由 `mapMessage` 从 `media_album_id` 映射。消息 id、顺序、read marker、删除/转发的语义都不变——相册只是渲染分组。
- **分组**:`groupMessages` 把 `messages[]` 折成「行」,虚拟列表的 `count`、行 key、未读分隔线、已读上报都按行计算;一行只画一个头像和一条时间/已读回执(取组内最后一条)。分组只折叠当前已加载且相邻的条目,历史页边界可能暂时留下半组,补页后自然合并;行 key 用 `a:<albumId>`,补页不会改名。
- **锚点**:阅读位置按行的首条消息 id 落库,滚动钩子按 `data-row-key` 找行;相册里某一条被删除后,剩下的条目退化成普通气泡。
- **布局**:2 列 116px 网格,奇数个时最后一格横跨两列;点击某一格仍打开那一条消息的「图片和视频」窗口。
- **暂不做**:相册级操作(回复/删除/转发/复制作用于被点中的那一条);发送端一次多选媒体仍是逐条发送,不合并成相册。

### 8.7 图片/视频的加载(对齐官方客户端)

气泡的加载不是「一挂载就下最大的那个文件」,而是官方客户端那套梯度。四件事:选尺寸、先出小图、按视口调度、视频边下边播。

- **尺寸选择。** 适配器把 TDLib 的 `photo.sizes` 整表映射成 `MessageMedia.sizes`(小→大);`fileId` 仍是最大图,供查看器、保存、复制使用。气泡按「盒子 × `devicePixelRatio`」用 `lib/mediaVariant.ts` 选**刚好盖住**的最小版本:240 px 气泡在 100% 缩放下要的是 320 那一档,不是 1280 的原图(体积差一个数量级,首屏时间也差一个量级);「图片和视频」窗口按窗口尺寸选;没有尺寸表(视频、文件)时退回 `fileId`。图已经落盘(`localUrl`)时不再下变体。
- **三级占位。** `minithumbnail`(约 40 px,模糊)→ `thumbFileId`(TDLib 的第二张小图,清晰,以更高的优先级先下)→ 正片用 `opacity` 过渡淡入替换。等待期间既没有空白,也不会「一张模糊块直接跳成大图」。
- **视口门控 + 取消。** 气泡复用 `lib/useInView.ts`(预载 `rootMargin` 约半屏):进范围才下载,出范围发 `media:cancel`。每个钩子实例是一个 **owner**;主进程 `media/leases.ts` 按文件计持有者,只有最后一个 owner 离开才 `cancelDownloadFile` —— 壳窗口的气泡和「图片和视频」窗口看同一张图时,先离开的那一个不会掐掉另一个的下载。优先级集中在 `lib/mediaPriority.ts`:32 保存/复制 > 28 播放中的视频 > 24 缩略图(可见)/18(近) > 16 气泡(可见)/8(近) > 4 音效 > 2 预览板。TDLib 同优先级是「后请求的先下」。
- **视频气泡只下封面。** 旧实现挂载即整包下载视频(几个视频就能把下载队列堵死),现在气泡只取 `thumbFileId` 做封面,片子交给「图片和视频」窗口。
- **流式播放(边下边播)。** `media:stream` 返回一种**流式 token**:registry 里存的是 `{ fileId }` 而不是路径。`wx-media://` 处理器遇到它时:
  1. `downloadFile(offset=Range.start, limit=0, synchronous=false)` —— 非阻塞,返回 TDLib 正在写的本地路径与 `expected_size`;seek 就是「用新 offset 再调一次」,TDLib 会丢掉上一段。**注意第一次调用的返回值是「排进下载队列之前」的文件状态**(冷文件 `local.path` 为空、`expected_size` 可能还是 0),路径要等随后的 update 才出现(实测冷启动 0:39 的片子约 500ms),所以这里轮询 `getFile`(100ms 一次,最多 4s)等状态稳定,不要拿第一次的答案判死;
  2. 反复问 `getFileDownloadedPrefixSize(fileId, offset)` 拿「从 offset 起连续可读多少字节」——**`stat` 的 size 不是可读长度**(TDLib 预分配的稀疏文件里未下载部分是空洞);
  3. 从磁盘按 256 KB 读出来推进响应体(`main/media/stream.ts`:纯 `StreamFeed` + `ReadableStream`,可单测),返回标准 206 + `content-range`,所以 `<video>` 能 seek;
  4. 空转时每 40 ms 轮询一次、每秒重新 `downloadFile` 推一下;连续 36 秒没有任何字节才让流失败;
  5. `request.signal` 中止(关窗口、元素放弃)就停泵,最后一个 owner 离开时取消下载。
- **查看器先画已有的图。** `ViewerItem` 带 `thumbFileId` / `sizes`;窗口先画气泡那张小图,正片到了原地替换;`onImageLoad` 只认正片,小图不能当缩放基准,否则 `lib/zoom.ts` 的 fit 会被 160 px 的图带偏。
- **契约变化(协议先行):** `MessageMedia.sizes?`、`ViewerItem.thumbFileId?/sizes?`、`media:download` 增加必填 `owner`、新增 `media:cancel` / `media:stream`。`media/registry.ts` 的 token 从「路径」扩成「路径 | fileId」联合体,已完成文件的既有行为(磁盘流 + Range)完全不变。

### 9.5 图片与视频查看:独立窗口

微信 4.x 点开图片或视频会**开一个新窗口**(窗口标题就叫「图片和视频」),而不是在聊天里
盖一层遮罩。复刻要点:

```
┌───────────────────────────────────────────────────────┐
│ 📌 │ ← → ▦ │ ⊕ ⊖ 1:1 │ ↻ │ ⇩ │               ─ □ ×  │ 40px 工具条(兼标题条)
├───────────────────────────────────────────────────────┤
│                                                       │
│                   图片(contain 居中)                 │
│                                                       │
└───────────────────────────────────────────────────────┘
```

- **窗口**:独立 `BrowserWindow`,`titleBarStyle: 'hidden'` + `titleBarOverlay`(高 40、
  底色与工具条一致),**普通顶层窗口(不设 `parent`)**,在所属显示器上居中。不设属主是为了
  任务栏像微信那样:同一进程的窗口按应用分组,一个 WeGram 图标、悬浮预览里列出「会话窗口」和
  「图片和视频」两格(实测 Windows 11:同进程 3 个窗口 → 一个按钮「3 个运行窗口」;属主窗口也
  照样在分组里,所以分组本身与拥有关系无关)。属主原本免费给的两件事因此改为显式:会话窗口
  `moveTop()` 抬高自己(见「定位到聊天位置」),以及会话窗口最小化/恢复时 `hide()/show()`
  查看窗口、关闭时一并 `closeViewer()`。尺寸取**屏幕的 75% × 90%**
  (实测 1536×864 上为 1147×774),与图片尺寸无关 —— 实测窗口里 591px 宽的图两侧留了大
  片留白;再按工作区钳位,最小 720×420(否则工具条放不下)。
- **工具条**:`-webkit-app-region: drag`,只画按钮;右侧预留 150px 给系统绘制的窗口控件。
  按钮 32×32、间距 8、组间 1px 分隔线;当前态(置顶/预览)用品牌绿。
- **图片区**:`#f7f7f7`(深色 `#242424`)画布,图片四周无内边距,缩放/平移/旋转全在
  CSS transform 上做,几何规则收在 `lib/zoom.ts`(纯函数、有单测)。
- **深色配色**(2026-11-18 于深色查看器窗口实测):工具条 `#3B3B3D`(比画布更亮,与会话
  列表同色;亮色主题里恰好相反,工具条比画布更暗)、画布 `#242424`、工具条字形 `#B1B1B1`、
  组间分隔线 `#4F4F51`、工具条下沿 1px `#2D2D2D`。对应 `--wx-viewer-bar` /
  `--wx-viewer-canvas` / `--wx-viewer-icon` / `--wx-viewer-sep`;原生 overlay 底色必须等于
  `--wx-viewer-bar`,否则标题条会露出一条接缝。
- **上一张/下一张**在渲染层已加载的同类媒体条里翻页:主窗口把 `ViewerItem[]` 和点击的
  index 经 `viewer:open` 交出去,查看窗口用 `viewer:init` 自取,不回主进程要历史。
  图片与视频各自成条(同一条里不混排),由 `lib/viewer.ts` 的 `buildViewerStrip` 收口。
- 交互:滚轮缩放、拖动平移、双击在「适应窗口/原始大小」间切换、← → 翻页、Esc 关闭。
- 更多菜单:复制 / 另存为… / 打印 / 转发… / 收藏 / 定位到聊天位置 / 使用系统默认方式打开;
  其中打印/转发/收藏协议层没有,点了只提示「还没有接入」(与「+」卡片同一约定)。
- **定位到聊天位置不关闭查看窗口**(微信会关,但微信的查看器本身就是同一窗口里的覆盖层,没有
  「抬窗口」这一步)。流程:查看窗口用 `viewer:locate` 交出当前条目的 `messageId`;主进程
  `restore()/show()` 之后 `moveTop()` + `focus()` 把会话窗口压到查看窗口之上,再用
  `evt:locate` 把 `{chatId, messageId}` 发给会话界面;会话界面打开该会话并落到那一行
  (不在已加载窗口里时先 `messages:around` 一页),列表把它滚到视口顶部并闪一下高亮
  (高亮是 1.6s 的动画,不是消息身上的状态)。两个窗口都是普通顶层窗口,抬高/压低就是普通的
  z-order,不需要临时改父子关系。

**视频窗口**是同一个窗口的另一种画布(实测:工具条完全相同,只是少了缩放/旋转组):

```
┌───────────────────────────────────────────────────────┐
│ 📌 │ ← → ▦ │ ⇩ │                              ─ □ ×  │ 40px 工具条(兼标题条)
├───────────────────────────────────────────────────────┤
│                    ┌───────────┐                      │
│                    │           │                      │
│                    │  视频     │  #f7f7f7 画布        │
│                    │ (按高适配)│                      │
│  ┌─────────────────┴───────────┴──────────────────┐   │
│  │ ▶ 00:01 ──●──────────────  00:51  倍速  🔊     │   │ 40px 播放条,浮在画面上
│  └────────────────────────────────────────────────┘   │

### 9.6 登录:扫码独立窗口

微信 4.x 的登录是先开一个独立小窗口、扫二维码;首次登录成功后直接进主窗口,以后启动时如果
有登录记录,才先停在「进入微信」资料页。复刻要点:

```
┌──────────────────────────────┐
│ WeGram                  ⚙  ✕ │ 32px 自绘标题条(整条 -webkit-app-region: drag)
├──────────────────────────────┤
│      ▛▀▀▀▀▀▀▀▀▀▀▜            │ 二维码 136×136,y=80:
│      ▌  QR CODE  ▐            │   TDLib 的 tg://login?token=…
│      ▙▄▄▄▄▄▄▄▄▄▄▟            │
│           扫码登录            │ 14px #00C375
│      用手机 Telegram 扫描二维码 │ 12px 灰
│                              │
│    用手机号登录  |  登录帮助    │ 14px 链接,文字底距 25px
└──────────────────────────────┘
```

- **窗口/标题条/页脚**:窗口 280×373(实测客户端 350×466 device px @125%)、`frame: false`、
  `resizable/maximizable/minimizable: false`,工作区居中,底色 `#FAFAFA`(深色 `#1E1E1F`);
  标题条 32px,自绘「WeGram + 齿轮 + ×」(14px `#6E6E73`、1.2px 细线 `#4D4D4D`、按钮
  28×28/间距 16/右内边距 8px),齿轮打开收窄后的 `ProxyPanel`;页脚 14px `#304B82` 链接,
  两项之间 1px 竖线。自绘 × 关闭自己,登录窗口是唯一窗口时关掉即退出应用。
- **扫码步骤(`waitQr`)**:主进程调 TDLib `requestQrCodeAuthentication`;TDLib 用
  `authorizationStateWaitOtherDeviceConfirmation.link` 给出 `tg://login?token=…` 并每几十秒
  换一次,映射为 `AuthState.waitQr { link }`。渲染层用 `qrcode`(MIT)把 link 编成 SVG:
  136×136(含四周 4 个模块宽的白色静区)/深色模块 `#2D2D2D`、白底;深色主题**不反色**
  (反色的二维码扫不出来)。静区必须画在二维码自己那一块里——登录窗口的底色是 `#FAFAFA`
  (深色 `#1E1E1F`),把页面当静区等于没有静区,手机相机找不到码。二维码
  只在渲染层生成,不经过主进程、不联网。绿色「扫码登录」14px,下面是 12px 提示;mock
  适配器另加一行「10 秒后自动模拟扫码」。
- **启动状态**:窗口在 `ready` 之前显示 `BootState` 的具体阶段(启动组件 / 打开本地数据库 /
  连接服务器 / 等待网络 / 同步数据),而不是一句「正在连接 Telegram…」。TDLib 起不来时停在
  「Telegram 连接未能启动」并显示 `failed.message`;客户端自己退出时停在「Telegram 连接已崩溃」
  并显示 `crashed.message`。两种终态都不再转圈,页脚只保留「登录帮助」——此时「用手机号登录」
  也是无效操作。
- **手机号回退**:TDLib 在 `waitOtherDeviceConfirmation` 状态下不接受
  `setAuthenticationPhoneNumber`,也没有取消二维码的接口。所以「用手机号登录」走
  `auth:reset`:主进程对当前 TDLib 实例 `destroy` 后重建(未登录时没有数据可丢),回到
  `waitPhoneNumber` 再显示原来的三步表单;手机号入口页可以「返回扫码」(`waitPhoneNumber`
  允许重新 `auth:qr`)。扫码后账号若开了两步验证,TDLib 进入 `waitPassword`,窗口显示密码
  步骤,提交后完成登录。网络不通时二维码会一直「正在获取」,8 秒后提示可以先设代理。
- **首次登录 vs 有登录记录**:主进程用 `authInteracted`(本次进程是否调用过
  `auth:qr/start/code/password/reset`)区分。用户驱动的登录到达 `ready` → 直接创建主窗口
  **并立即关闭**登录窗口,不停资料页;启动时 TDLib 复用 session(`authInteracted` 为 false)
  才停在资料页,点「进入 WeGram」(`login:enter`)开主窗口。
- **资料页(`ready`)**:头像 80×80 圆角 12(无照片用首字母色块)、名字 16px `#191919`、
  168×36 绿色按钮「进入 WeGram」;页脚「切换账号 | 登录帮助」,切换账号走 `auth:logout`
  回扫码步骤。
- **窗口切换**(主进程 `main/index.ts`):启动只开登录窗口;登录完成或退出登录都先建目标
  窗口、再关旧窗口。首次登录的立即关闭也满足这一点——主窗口已经存在(隐藏)时才关登录
  窗口,所以 `window-all-closed` 只在用户关掉唯一窗口时触发。
- **事件与路由**:登录窗口只处理 `evt:auth`,不引导 store(不拉会话列表);同一渲染包用
  `#login` 加载(与 `#viewer` 同一约定);浏览器预览用 `http://localhost:5174/#login`。
- **深色**:`#1E1E1F` 底、`#2F2F30` 输入框、`#E1E1E5` 文字、`#7D90B8` 链接;**没有**在客户端
  深色登录窗口上实测。
- **未实测**:真实扫码链路(需要手机 Telegram 扫一次窗口里的二维码)和 `auth:reset` 在真实
  TDLib 上的 destroy/重建;mock 与浏览器预览已覆盖 UI 的两条路径。

### 9.7 通讯录:联系人面板

微信的「通讯录」不是第二个会话列表:左列是「通讯录管理 + 服务入口 + 按首字母分组的联系人」,
右列是选中联系人的资料卡(不是聊天窗口)。WeGram 用 Telegram 的**通讯录**(TDLib
`getContacts`)充当联系人:一行是一个「人」,不是一段会话。

```
┌───────────────┬──────────────────────────────┐
│ 搜索           │  [60px 头像]  名字        ⋯  │
│ ┌───────────┐ │            Telegram号：xxx    │
│ │ 通讯录管理 │ │  ──────────────────────────  │
│ └───────────┘ │  朋友资料                    │
│ › 新的朋友     │  备注      添加备注名         │
│ › 公众号、服务号 │ ──────────────────────────  │
│ › 企业微信联系人 │  更多信息                    │
│ › 我的企业      │  数据中心  DC 5              │
│ ⌄ 联系人        │  手机号    +8613800000000    │
│   A            │  ──────────────────────────  │
│   [30] 名字     │   ◯发消息   ☎语音聊天  ▣视频  │
└───────────────┴──────────────────────────────┘
```

- **数据**:TDLib 的 `getContacts`(账号通讯录),每个 user id 再用 `getUser` 取
  名字/username/phone;一个从没聊过的人也有资料卡,而**没有会话**。名字 = `first_name`
  + `last_name`,空则退回 username,再空则 `用户 <id>`。按名字首字母分组:汉字用 ICU 的
  中文排序(拼音)找首字母,拉丁字母直接取大写,其余(数字/emoji/其他文字)进 `#` 组,
  `#` 永远最后。已删除/取不到的用户跳过,不让一条坏记录清空整个通讯录。头像来自
  `evt:avatars`(user id → `wx-media://`),与聊天列表同一套缓存。
- **左列尺寸**(125% 截图换算成 CSS px):列宽 238(沿用会话列);搜索 26 高;通讯录管理
  35 高、8 圆角、16px 字;服务入口行 36 高;分组头 30 高、13px;联系人行 54 高、30px
  圆角 4 头像、16px 名字;计数 13px `#9F9FA6`。服务入口的 `›` 与「联系人」的 `⌄` 都是
  #0555 那个 12px 箭头旋转,不另挖图标。
- **右列资料卡**:固定 310px 居中(不随窗口变宽),上内边距 59;头像 60 圆角 6;名字
  17/500;`Telegram号：` 14px `#6E6E73`,值就是 `contacts:list` 带回的 username(没有就写
  「未设置」);头像下 19px 一条 `#F0F0F0` 细线;每个分区上 20/下 10(更多信息下 16);
  标签列 72;三个动作 96 宽 × 24 图标 + 8 间距 + 14px 文案,蓝 `#304B82`(深色
  `#7D90B8`),顶部 30、左右 11;选中的联系人行是中性灰 `rgba(0,0,0,.08)`,不是聊天
  列表的绿色。
- **IPC**:新增 `contacts:list → Contact[]`(`{ userId, title, username?, phone?,
  avatarUrl?, dcId? }`,schema 在 `packages/protocol/src/contact.ts`:`dto.ts` 已到 550 行上限)。
  适配器侧在 `tdlib/actions/contacts.ts`(`getContacts` → `getUser` → `map/contact.ts`),
  头像用 `prefetchUserAvatars` 后台下载。`getContacts` 一次给全部 id,没有分页参数。
  「发消息」走已有的 `chats:openPrivate { userId }`(`createPrivateChat`):会话在点下去时
  才创建,创建后照常出现在聊天列表里。
- **映射**:公众号、服务号 = 频道数(仍来自 `chats:list`,不是通讯录);新的朋友 /
  企业微信联系人 / 我的企业 / 通讯录管理 / 备注 / 语音聊天 / 视频聊天 / 更多资料在
  Telegram 没有对应数据,保留位置但点击只提示「还没有接入」(与「+」卡片同一约定)。
  「发消息」= 打开该私聊并切回聊天分区。
- **数据中心**:TDLib 的 `user`/`userFullInfo`/`profilePhoto` 都不带 DC,MTProto 的
  `userProfilePhoto.dc_id`(Pyrogram 的 `user.dc_id`)是客户端唯一的 DC 信号。TDLib 把它
  编进了文件的持久 id:`base64url(zeroEncode(serialize(location)) + [版本, 持久 id 版本])`,
  前两个 int32(小端)是 `FileType` 和 DC。`tdlib/file-dc.ts` 解这段内部格式并做校验
  (版本字节、FileType 范围、DC 1–5),取不到就显示「未知」——没有头像的人没有 DC。
  注意这是**近似值**:DC 是「头像所在机房」,Pyrogram 文档也说明它只是近似用户所在 DC。
- **限制**:列表就是账号在 Telegram 的通讯录(本机实测 4 条);没有虚拟列表(几百行以内
  没问题);机器人如果被加进通讯录也会出现;`getContacts` 不带分页,一次全量返回。
  TDLib 给的真实号码不带 `+`,资料卡显示时补上(见 `lib/format.ts` 的 `formatPhone`)。

### 9.8 消息下面的评论:Telegram 消息线程

微信里一条群消息(尤其是文章卡片)下面会挂一行「78 条评论 ›」,点开是评论列表。WeGram 的数据
来源是 Telegram 的**消息线程**:频道帖子的评论区就是它关联的讨论组,讨论组里每条帖子下面的回复
也属于同一个线程。TDLib 把数量放在 `message.interaction_info` 里,画评论条不需要额外请求;
展开时才按线程拉一页评论(`getMessageThreadHistory`)。

评论条只是入口;点开的是 Telegram 那样的**讨论视图**:整块会话面板被一块从右侧滑入的面板盖住。

群聊/私聊里的评论条是气泡下面的一行;频道帖子(频道是一个人在发帖,不是一群人在聊天)则按
Telegram 的样子把**图片、正文说明和评论入口放进同一个气泡**,外观仍是微信的气泡(同样的
填充、圆角和头像列),气泡右下角是阅读数和时间:

```
[头像] 名字
       ┌────────────────────────┐
       │ 帖子正文 / 媒体          │
       └────────────────────────┘
       ┌────────────────────────┐   ← 只有 comments > 0 才画
       │ 评论 78 条           ›  │   ← 点开:全屏面板自右向左滑入
       └────────────────────────┘

频道帖子(同一块气泡,不拆第二条):
[头像] 频道名
       ┌────────────────────────────┐
       │ 图片(3px 内衬)              │
       │ 说明文字        👁 1.2万 23:31 │  ← 阅读数 · 时间
       ├────────────────────────────┤  ← 只有 canOpen 才画
       │ 评论 78 条               ›  │
       └────────────────────────────┘

面板(盖住整个会话列,标题栏和输入栏一起):
┌────────────────────────────────────────┐
│ ‹  评论                                 │  ← 46px 标题栏
│    78 条评论                            │
├────────────────────────────────────────┤
│ [36] Telegram News  频道消息…           │  ← 被评论的消息钉在顶部
├────────────────────────────────────────┤
│ [34] 小满   18:48                      │
│      这条我先收藏了，晚点对着改。        │
│ [34] 阿星   18:50                      │
│      同问 +1，我也卡在这一步。           │
│ …(滚到顶部自动加载更早一页)              │
└────────────────────────────────────────┘
```

- **数据**:`messageInteractionInfo` → `views`(`view_count`,频道才有真实值)、
  `forwards`(`forward_count`)、`comments`(`reply_info.reply_count`)、
  `canOpen`(有没有 `reply_info`)。TDLib 1.8.70 的 `message` **没有 `properties` 字段**
  (「能不能拉这条线程」只能靠 `getMessageProperties` 单查一次),所以「这个帖子有评论区」
  就用「有没有 `reply_info`」当信号。**但只有频道帖子才画**:TDLib 也会给关联讨论组里的
  普通消息填 `reply_info`,只按计数画的话群成员的消息下面会冒出「写评论」,而官方客户端一条
  都不画(桌面端要解析出当前会话的关联讨论频道 `checkDiscussionLink`,安卓要
  `hasDiscussion && isLinkedToChat`;2026-11-21 在 Telegram Desktop 7.4.5 上实测确认,
  同一批群消息官方没有任何评论条)。所以 `isCommentablePost` 只放行**频道里的帖子**,
  群聊/私聊里的一律不画——讨论组的历史里只有评论、没有帖子本体,那条线程本客户端也打不开。
  `interaction_info`
  缺失时整块不渲染;**`comments === 0` 但 `canOpen` 为真时仍然画条**,文案「写评论」——
  评论区存在、只是还没人说话,官方客户端也是这个入口。
- **IPC**:消息 DTO 新增可选 `interaction`;新增 `messages:comments { chatId, messageId,
  fromMessageId?, limit ≤ 100 } → { messages, hasMore }`。频道帖子把 `chat_id` 传频道
  本身,TDLib 自己路由到关联讨论组;接口原样返回倒序,适配器统一排成升序。`from_message_id`
  是「从这条往前」的游标,和 `getChatHistory` 一样用于翻更早的评论。评论线程的阅读位置走
  `ui:saveCommentAnchor` / `ui:getCommentAnchor`(`{ chatId, messageId }` 定位线程),落 `ui.db`
  的 `comment_ui_state`,与会话的 `ui:saveAnchor` 是两张表、互不覆盖。
- **实时**:`updateMessageInteractionInfo` 只带 `chat_id`/`message_id`/`interaction_info`,
  所以不重取整条消息,只发 `messageOp: { op: 'interaction' }`,渲染层原位合并那条消息上的计数
  ——阅读数变化很频繁,整条重映射太贵。**这个 op 是部分补丁**:TDLib 手里没有回复数据时
  `interaction_info` 里根本没有 `reply_info`,旧代码兜底成 `{ comments: 0 }` 会把首屏拿到的
  真实评论数抹成 0,评论条当场消失(下次重载才回来)。所以只在真带了 `reply_info` 时才写
  `comments`/`canOpen`,只带 `view_count` 的更新就只更新阅读数。
- **渲染**:评论条只画在频道帖子上(见上一条的 `isCommentablePost`),群聊/私聊里的消息不画。
  **频道帖子**:图片(3px 内衬)、说明文字、右下角的「阅读数 · 时间」
  和评论条都在同一个微信气泡里——评论条是气泡的最后一行,顶部一条 hairline 分隔、左右下三个角
  共用气泡圆角,像 Telegram 的频道帖。阅读数用 `formatCount`(1.2万),没有 `views` 时只画时间;
  频道帖子的时间不再走 hover 行,气泡里常显。媒体贴的气泡最大 420×480(普通消息仍是 240×300),
  而且**气泡宽度就取媒体宽度**:说明文字在这个宽度内换行,不会把气泡撑得比图片宽、在图片右边留一条
  空缝(否则 `fit-content` 会按最长的文字行定宽)。评论条**占满气泡整行**:用
  `width: calc(100% + 2 × 内衬)` 配合负外边距贴到气泡左右内边(只用 `auto` 时按钮会缩成标签
  那么宽,看起来只有左下角一小块)。点开 `CommentPanel`:绝对定位盖住整个 `.wx-chat`(`inset: 0`,聊天列在面板存在
  期间 `overflow: hidden`),用 `transform: translateX(100%) → 0` 的 250ms ease-out 滑入,关闭
  反向滑出,父组件等动画结束(`COMMENT_PANEL_ANIM_MS`)才卸载,所以进出都不闪;`prefers-
  reduced-motion` 时直接切换。面板自带 46px 标题栏(‹ 返回 / `评论` / `N 条评论`),被评论的
  消息(头像 + 名字 + 三行截断的正文,频道消息下面一行「阅读 · 转发」)钉在列表上方。
  列表**默认落在最上面**(已加载的一页里最早那条评论,紧贴被评论的消息下方),不是最新一条——
  频道的评论按微信的习惯从头往下读。读者滚动时,把第一条可见评论的 id 和它的偏移按
  `(chatId, messageId)` 写进 `ui.db`;再次打开这个线程就恢复那一行,和会话的阅读位置同一套
  规则。存下的行不在已加载窗口里(重启后只拉最新一页)时落回顶部,而不是一页一页往回翻。
  滚到距顶 90px 内自动用最旧一条的 id 拉下一页,并在插入后补偿 `scrollTop`,阅读位置不跳。
  Esc 与返回键都关闭;加载中/失败/空各一行文案,失败可重试;
  取过的页按 `(chatId, messageId)` 缓存在渲染层,再次打开立即显示。
- **评论就是普通消息**:评论行直接用消息列表的 `MessageRow`(`chat.kind='group'` 的伪会话),
  所以头像、发送者、气泡、hover 时间、图片/贴纸/图文都跟聊天里一模一样,自己的评论是右侧绿色
  气泡;评论里的 `interaction` 会被剥掉,避免评论再开一层讨论视图。面板底部是聊天输入框的卡片
  (同一个 `.wx-composer` 结构:圆角描边卡片 + 发送按钮),占位「写评论…」。
- **发评论**:Enter 发送(Shift+Enter 换行,IME 组合期间不发送)。`messages:sendComment` 让适配器
  先 `getMessageThread` 拿到讨论组的 `chat_id` 和线程根 id,再往讨论组 `sendMessage` 并对线程根
  `reply_to`(回复某条评论时换成那条的 id)。返回的消息直接追加到面板并滚到底;帖子上的计数由
  `updateMessageInteractionInfo` 的 `interaction` op 回填(面板拿到的是 store 里的实时消息,不是
  打开时的快照)。发送本身**不会自动加入**讨论组(官方客户端也不这么做)。
- **能不能发**:和官方客户端一样,不向服务器要 "canComment",而是 `messages:commentInfo` 按
  tdesktop 的规则组合:讨论组的 `supergroup.status`(成员状态)、`join_to_send_messages`、
  `usernames`(是否有公开链接)、`chat.permissions.can_send_basic_messages`、受限成员自己的
  `permissions`、管理员/群主、`join_by_request`,加上慢速模式的剩余秒数;纯函数在
  `main/telegram/comment-access.ts`,单测覆盖。`join_to_send_messages` 在讨论组里**默认可以为
  false**,所以公开讨论组不加入也能评论。不能发且不是成员时,面板底部换成「加入讨论组」/
  「申请加入讨论组」按钮(`messages:joinCommentGroup` → `joinChat`,`chatJoinResultSuccess` 直接
  可用、`chatJoinResultRequestSent` 显示「等待管理员通过」),之后重新判定;被禁言/封禁只显示只读
  文案。慢速模式下发送按钮按剩余秒数倒计时禁用,发完再查一次。
- **限制**:评论面板只发文本,不发送媒体/贴纸;申请制的讨论组要等管理员同意;守卫机器人
  (`chatJoinResultGuardBotApprovalRequired`)不接管,直接报错。
- **尺寸**:标题栏 46(与会话头一致);帖子头像 36 圆角 5,评论头像 34 圆角 4;列表内边距
  14/18、行间 14;评论条高 30、上间距 5、左内边距 12、13px 字 `--wx-text-secondary`。
- **不做**:评论的编辑/删除/点赞(以及在看、表情:Telegram 的 `reactions` 是另一套语义,留给
  后续);评论里发图片/贴纸(面板只发文本)。阅读/转发只作为帖子下面的一行小字,不放进聊天流。

## 9.9 聊天信息:压在消息上的侧面板

会话头右上角的「…」不再弹调试小卡片,而是打开客户端 4.x 的 **聊天信息** 面板(2026-11-21;
群聊排版按客户端的群聊截图补齐)。

- **位置与压盖**:从会话头下方开始(标题栏与会话头保持全宽),宽 314,左缘一条 1px `#f0f0f0`。
  它是**覆盖层**:从右向左滑入,压在聊天流和输入框之上,底下的消息宽度不变 —— 面板开合绝不能让
  任何一行消息重排。动画因此只有 `transform: translateX(100% → 0)`(200ms);收起时父组件按
  `INFO_PANEL_ANIM_MS` 保留面板再卸载。
- **私聊**:对方头像 + 名字;查找聊天内容、消息免打扰、置顶聊天、清空聊天记录。
- **群聊**(按客户端排版):顶部「搜索群成员」输入框、成员格 + 虚线「添加」,然后 群聊名称 /
  群公告 两条上下排列的信息行(标签 14 + 灰色说明 12),再是 群二维码、查找聊天内容、
  消息免打扰 / 置顶聊天、清空聊天记录、退出群聊。
- **概念映射**(微信有、Telegram 没有的行,写清代价):
  - 群聊名称 → `setChatTitle`(需要 `can_change_info`);成功后 toast,标题、列表、面板一起更新。
  - 群公告 → Telegram 的**最新置顶消息**(`getChatPinnedMessage`;404 表示没设置,行上写
    「群主未设置」)。点一下走定位链路跳到那条消息;不新增公告字段。
  - 群二维码 → **独立的小窗口**(见下条)。链接本身:窗口要的是客户端的**临时码**,
    即 `createChatInviteLink` + 7 天过期(`chats:inviteLink { temporary: true }`);没有管理员权限
    时退回公开用户名(`https://t.me/<username>`)或本账号已有链接,此时有效期文案改成「长期有效」。
    都没有就写明拿不到的原因。「添加」仍然打开面板内的邀请链接弹窗(Telegram 里邀请=分享链接)。
  - 退出群聊 → `leaveChat`,并显式发 `remove` chat op(main 不等 TDLib 的后续 update)。
  - **不做**:备注、我在本群的昵称、保存到通讯录、显示群成员昵称。Telegram 没有对应物 —— 昵称就是
    资料名,群永远在会话列表里,发送者名始终显示;这些留给以后做本地扩展时再谈。
- **成员格**:每格 66 宽;头像 47、圆角 4;名字 12px `#9f9fa6`、单行省略。「搜索群成员」是
  服务端搜索(`searchChatMembers` 带 query,260ms 防抖),不是过滤已加载的 12 个;照片走既有的
  `evt:avatars` 池。私聊、以及没有管理员权限拿不到成员表的频道,退回会话自身的头像。
- **行与开关**:链接行 64 高、右缩进 33 给箭头/开关;免打扰与置顶共用一个上下 10px、每行 41 的块;
  红行 64 高居中;分割线左右内缩 18/19。开关是 36×20 胶囊,滑块 16,关 `#ededed`、开 `#00c375`
  (登录窗的绿,不是品牌绿)。
- **查找聊天内容**:面板内搜索视图(260ms 防抖),走 `search:inChat`(TDLib 自己的索引,不是过滤
  已加载的一页),结果按时间倒序;点一条即收起面板,复用 `requestLocate`(必要时
  `messages:around` 拉一圈窗口)。
- **群二维码窗口**:点击 群二维码 打开 360×560 的无边框小窗(父窗口是主窗口,随主窗口关闭/
  最小化;任务栏不单独出现)。内容是客户端的排版:群头像拼贴(最多 6 个成员头像,单人就画会话头像)、
  「群聊：前 3 个成员名」、280 px 二维码、一行有效期,底部三按钮 转发给朋友 / 复制图片 / 保存图片。
  - 图片由窗口自己栅格化:和屏幕上的 SVG 用同一个 `qrMatrix`/`qrDrawing`,输出 1024 px PNG
    (含 4 模块静区)。
  - 复制走主进程剪贴板(`qr:copy`,与查看器的 复制 同一套 web clipboard);保存走原生保存对话框
    (`qr:save` → 图片目录);转发把 PNG 作为**图片消息**发给选中的会话(`qr:share`:主进程写临时
    文件 → 适配器 `sendMedia` → 删除),会话列表由 `chats:list` 拉取,窗口内自带选择列表。
  - 有效期文案:临时码显示「该二维码 7 天内（<M月D日>前）有效，重新进入将更新」;公开/长期链接显示
    「该链接长期有效，重新进入不会变化」。每次打开都会生成一个新的 7 天链接(微信的「重新进入将更新」),
    旧链接 7 天后自然过期。
  - Esc 先关转发列表再关窗口;× 与 Esc 都走 `qr:close`(无边框窗口没有原生关闭控件)。
- **关闭**:再次点「…」、Esc(先关最上层弹窗或搜索视图,再关面板)、切换会话;打开评论面板前
  先关掉它。

## 10. 安全

- **api_id / api_hash 必须自己在 [my.telegram.org/apps](https://my.telegram.org/apps) 申请**。复用官方客户端或开源项目内置的凭据违反 [API ToS 2.1](https://core.telegram.org/api/terms),会被封号。
- session 由 TDLib 存盘,整个 `tdlib/` 目录用 `safeStorage`(Windows DPAPI)加密或放在受保护目录;2FA 密码只在内存中存活,永不落盘。
- 渲染层禁用 `nodeIntegration`,所有文件访问经主进程白名单校验路径(防目录穿越)。
- 外链一律 `shell.openExternal` + 协议白名单。
- 代理密码与 MTProxy `secret` 与应用凭据同级处理:只在内存与 `safeStorage` 密文中存在,渲染层只拿掩码。
- 贴纸/自定义 emoji 的 TGS 与 WebM 是**用户可控二进制**,解压与解码必须限大小(单文件上限 + 解压比上限),防止 gzip 炸弹与超大 Lottie 卡死渲染进程。
- 不要实现任何批量群发/自动加人功能——这是封号的第一原因,也会牵连你的 api_id。
